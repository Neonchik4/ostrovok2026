## Фича "Отзывы" — НЕ РЕАЛИЗОВЫВАТЬ СЕЙЧАС, подробный план для Gemini 3.8 Flash

> Этот раздел написан как самодостаточное техзадание для другой модели (Gemini 3.8 Flash),
> без контекста предыдущего чата. Содержит всё необходимое: что не так сейчас, почему,
> что нужно сделать, где именно в коде, какие ограничения проекта соблюдать.

### Контекст и почему это НЕ было сделано раньше

Проект — AI-агент поиска отелей для хакатона «О!Хакатон 2026» (Островок). Правила проекта закреплены в `AGENTS.md`, раздел 1.2 «Запрет хардкода и моков (Real Responses Only, 99% Real Data)»: категорически запрещены «заготовленные шаблоны ответов» и синтетические заглушки в рабочем коде.

Датасет отелей (`outputs/hotels_dataset.json`, 2666 шт.) собран реальным скрапером `scripts/parse_ostrovok_hotels.py` — он ходит на живой `ostrovok.ru`, парсит `__NEXT_DATA__` из SSR-каталога и берёт оттуда реальные `name`, `stars`, `rating`, `reviews_count`, координаты, цены. **НО** поле `reviews_summary` (см. `scripts/parse_ostrovok_hotels.py:356-367`) для текста отзывов — синтетика: `review_snippets` — это захардкоженная строка `f"Отличный отель в {city}, номер соответствовал фотографиям. Обязательно вернемся снова!"`, **одна и та же для всех 2666 отелей**. `positive_highlights`/`negative_highlights` — тоже статичные списки-константы, не привязанные к конкретному отелю.

Строить фичу "фильтр/ранжирование по отзывам" на этих данных как есть — прямое нарушение AGENTS.md 1.2, потому что пользователь увидит идентичный "отзыв" под разными отелями. Поэтому фича заблокирована до тех пор, пока не появятся **настоящие** тексты отзывов.

### Что нужно сделать (3 этапа)

**Этап 1 — реальный парсинг текста отзывов (ETL, офлайн, не в рантайме).**

Расширить `scripts/parse_ostrovok_hotels.py` (он уже умеет ходить на `ostrovok.ru` и кэширует ответы в `outputs/raw_ostrovok/` — паттерн переиспользовать). Сейчас скрипт берёт данные только со страниц **каталога** (список отелей). Нужно:
1. Для каждого `hotel_id`/`slug` дополнительно зайти на страницу **карточки конкретного отеля** (обычно `https://ostrovok.ru/hotel/{region_slug}/{hotel_slug}/` или аналогичный паттерн — уточнить реальный URL по структуре сайта, посмотреть `__NEXT_DATA__` на живой карточке отеля вручную перед тем как писать код).
2. Найти в `__NEXT_DATA__` карточки блок с отзывами (обычно `pageProps.reviews` или похожий путь — определяется через ручной осмотр JSON, аналогично тому, как в `fetch_page_cached` находится `serpData.hotels`).
3. Вытащить реальный текст 5-15 отзывов на отель (не сотни — иначе слишком долгий прогон и слишком большой объём для LLM-этапа).
4. Сохранить сырые отзывы в `outputs/raw_reviews/{hotel_id}.json`, аналогично кэшу каталога — чтобы при сбое не начинать заново.
5. **Соблюдать вежливость**: та же пауза `time.sleep(random.uniform(0.35, 0.65))` между запросами, что уже есть в скрипте. Это x2666 дополнительных запросов (по одному на отель) — прогон может занять часы, планировать заранее, не в последний день.

**Этап 2 — офлайн LLM-тегирование (батч-скрипт, отдельно от боевого рантайма).**

Новый скрипт, например `scripts/tag_reviews.py`:
1. Для каждого отеля взять сырые отзывы из `outputs/raw_reviews/{hotel_id}.json`.
2. Одним LLM-вызовом (Gemini, через существующий `backend/app/services/llm_client.py` — переиспользовать каскад ключей×моделей, не писать новый клиент) на отель попросить модель:
   - выделить 2-4 реальные короткие цитаты (не выдумывать, только сокращать/выбирать из присланного текста)
   - проставить булевые теги на основе реального текста: `quiet` (тихо/шумно), `romantic` (романтично/атмосферно), `sea_view`/`mountain_view`/`city_view` (упоминание вида, если есть), `noise_complaints` (явные жалобы на шум/музыку/соседей)
   - вернуть строгий JSON (тот же паттерн prompted-JSON, что уже используется в `backend/app/services/slot_extractor.py` — скопировать подход к парсингу ответа)
3. Обязательно: если реальных отзывов для отеля не нашлось на этапе 1 (сайт не отдал, ошибка, у отеля их физически 0) — **не выдумывать** ничего, оставить поля `null`/пустыми и это ДОЛЖНО быть видно на фронте как "отзывов пока недостаточно", а не как отсутствие тегов (фронт не должен молча трактовать пустоту как "всё плохо").
4. Записать результат обратно в `outputs/hotels_dataset.json` (поле `reviews_summary`, заменить синтетические placeholder на реальные), и пересобрать векторный индекс через существующий `scripts/build_chroma_index.py`.
5. Это разовый батч-прогон **до** демо, не рантайм-вызов — планировать во время, когда не идёт демонстрация жюри, потому что это тоже расходует RPD-бюджет тех же Gemini-ключей, что и боевой чат.

**Этап 3 — использование тегов в поиске (рантайм).**

1. В `backend/app/services/hotel_filters.py` — при матчинге `semantic_query`/мягких критериев пользователя (например "тихо", "романтично", "вид на море") в первую очередь проверять новые структурные теги из `reviews_summary` (появившиеся на этапе 2), и только если тега нет — падать назад на нынешнее нечёткое совпадение по `description`/embedding.
2. Показывать в UI карточки отеля рядом с найденным критерием пометку, что это подтверждено реальным отзывом, и **сколько именно отзывов было проанализировано** (прозрачность вместо "доверьтесь нам") — например "на основе 8 отзывов".
3. Не делать hard-фильтр по отзывам (не скрывать отель полностью) — только мягкий ranking-сигнал/бонус к скору, чтобы один нерепрезентативный отзыв не выкидывал нормальный отель из выдачи.
4. Защита от накрутки/фейковых отзывов (когда данные реальные): не доверять единичному отзыву, смотреть на согласованность нескольких отзывов одного отеля; при явно шаблонных/подозрительно одинаковых по структуре отзывах — не использовать для тегирования этого отеля, оставить как "недостаточно данных".

### Ограничения, которые нельзя нарушать при реализации

- Никакого хардкода/заглушек текста отзывов в рабочем коде (`backend/app/`) — это именно то, ради чего вся фича затевается, нарушать нельзя даже частично (например "один дефолтный отзыв, если парсинг не удался" — запрещено, см. AGENTS.md 1.2).
- Файлы до 200-250 строк (AGENTS.md 1.5.3, SRP) — не пихать всю логику в один файл, разбивать по паттерну, который уже есть в проекте (`hotel_filters.py`, `slot_extractor.py` как примеры разделения).
- Тесты сначала (TDD, AGENTS.md 1.5.1) — для нового кода в `backend/app/services/` сначала написать тест в `backend/tests/`, потом реализацию.
- Санитизация текста отзывов при парсинге (если он попадёт в промпт LLM) — использовать существующий `sanitize_user_input`, не передавать сырой HTML/непроверенный текст напрямую в промпт без очистки.
- Не запускать Этап 1 и Этап 2 в день демо — они расходуют тот же RPD-бюджет Gemini, что и боевой каскад чата, и нужны на VPS/локально заранее.
