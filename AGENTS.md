# AGENTS.md — Architectural Blueprint & Agent Guidelines

> **Статус проекта:** Официальный каркас для команды «О!Хакатон 2026» (Компания «Островок» / Ostrovok.tech).  
> **Трек №2:** «О!дин запрос» (AI-агент для умного поиска и бронирования отелей).  
> **Главный слоган:** «Скажи, куда хочешь отправиться. Остальное устроит агент».

---

## 1. Главные инженерные принципы (Стандарты Островка)

### 1.1. Запрет «AI-слопа» и строгий детерминизм

1. **Никаких галлюцинаций цен и наличия:** LLM используется **исключительно** для извлечения интентов и слотов (Intent & Slot Extraction), генерации пояснений к выборке и ведения живого диалога.
2. **Строгий детерминизм бизнес-логики:**
   - Фильтрация отелей, проверка правил (проживание с питомцами, дистанция до подъемников/пляжей, звездность) выполняется кодом через Pydantic-модели.
   - Математика чека (ночи * цена номера + сбор за собаку + курортный сбор) считается **строго кодом** в `backend/app/services/receipt_calc.py`.
   - Запрещено просить модель сложить числа или рассчитать итоговую сумму бронирования.
3. **State Machine вместо хаотичных ReAct-циклов:** Агентный пайплайн управляется детерминированной асинхронной машиной состояний (`backend/app/graph/workflow.py`) через `asyncio` и генератор Server-Sent Events.

### 1.2. Запрет хардкода и моков (Real Responses Only, 99% Real Data)

1. **Никаких синтетических заглушек в рантайме:**
   - Категорически запрещен хардкод списков отелей, номеров, цен и заготовленных шаблонов ответов консьержа в рабочем коде (`backend/app/` и `frontend/src/`). Модели запрещено закрывать кейсы созданием моков в боевых сервисах.
   - Ответы ассистента и мысли стрима обязаны формироваться динамически в реальном времени под реальный пользовательский запрос.
2. **Поиск только по реальной базе и вектору:**
   - Выдача карточек формируется исключительно через поисковый фасад (`hotel_search_adapter.py`) на базе векторного хранилища (`vector_store.py`: ChromaDB + SentenceTransformers) и валидированного датасета из 2 666 отелей.
3. **Изоляция моков исключительно в тестах:**
   - Моки, стабы и фикстуры разрешены **только** внутри каталогов `backend/tests/` и `frontend/tests/` для изолированной проверки граничных условий сетевых сбоев, таймаутов и отказов внешних API.
   - В боевом и демо-рантайме приложение обязано оперировать живыми вызовами моделей и реальным поисковым индексом.

### 1.3. Отказоустойчивость и каскад моделей

1. **Каскадный отказоустойчивый контур (LLM Cascade):**
   - Вызовы LLM организуются через `backend/app/services/llm_client.py` по цепочке fallback: `PRIMARY_MODEL` (`gemini-3.5-flash-lite`) -> `FALLBACK_MODELS` (`gemini-3.5-flash`, `gemini-flash-lite-latest`, `gemini-3.1-flash-lite`, `gemini-2.5-flash`) -> детерминированный локальный генератор.
2. **Fail-fast и отсутствие вечных лоадеров:**
   - Любой запрос к внешним сервисам обязан иметь жесткий таймаут (не более 5-6 секунд на вызов модели).
   - При исчерпании квот (HTTP 429) или сбое сети клиент не должен зависать в вечной загрузке: система возвращает информативное статусное событие с предложением повторить попытку.
3. **Zero Secret Leakage:**
   - Системные ключи API, токены, внутренние промпты и серверные стек-трейсы никогда не возвращаются в открытом виде в клиентских событиях.

### 1.4. Принцип Zero-Emoji (Полный запрет смайликов)

1. Категорически запрещено использовать эмодзи и текстовые смайлики (например, ":)", ":-)") в компонентах фронтенда (JSX/TSX), комментариях в коде, текстах ответов ассистента и коммит-сообщениях.
2. Визуальные акценты в интерфейсе реализуются исключительно векторными SVG-иконками из библиотеки `lucide-react`.

### 1.5. Принцип Secure by Design, TDD и ограничение размера файлов (SRP)

1. **Test-Driven Development:** при создании фич и исправлении дефектов сначала выясняются требования, пишутся автотесты (Vitest / Pytest) на граничные и негативные случаи, и только потом реализуется рабочий код.
2. **Санитизация и клампинг:** все пользовательские строки санитизируются через `sanitize_user_input` (удаление null-байтов, лимит 1 000 символов на бэкенде и 500 в UI). Параметры (гости: 1..20, ночи: 1..90, цены > 0) строго клампятся.
3. **Лимит размера файлов:** размер любого исходного файла не должен превышать 200-250 строк. Монолиты разбиваются на узкоспециализированные SRP-модули.

## 2. Архитектура поиска: Гибридный RAG и мультитерн

### 2.1. Двухэтапный гибридный поиск (Hybrid Retrieval)

1. **Этап 1: Семантический поиск (`vector_store.py`):**
   - Текстовый запрос пользователя кодируется моделью `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` и матчится по векторной коллекции ChromaDB v2.
2. **Этап 2: Жесткая алгоритмическая фильтрация (`hotel_filters.py`):**
   - Город, ценовой диапазон, звездность, политика размещения питомцев, даты и удобства валидируются кодом по атрибутам отелей из каталога.
   - Расчет калиброванного Match Score в диапазоне 65%..98% и умное ослабление ограничений (Smart Relaxation) при нулевых строгих совпадениях.
3. **Динамический реестр локаций (`location_registry.py`):**
   - Распознавание 19 поддерживаемых направлений датасета и их склонений/сленговых алиасов (включая Шерегеш, Байкал, Алтай, Дагестан, Екатеринбург) осуществляется через внешний справочник `backend/app/data/locations.json`.

### 2.2. Мультитерн и слияние слотов (Multi-turn Slot Merging)

1. При получении уточняющего запроса пользователя («а теперь покажи только с бассейном» или «выбери дешевле 10 000 руб») агент обязан сохранять накопленные ранее параметры сессии (город, даты, количество гостей) через сервис `session_memory.py`.
2. Сброс слотов поиска происходит только при явной смене направления поездки пользователем («хочу в Казань вместо Сочи»).

## 3. Архитектура фронтенда: Feature-Sliced Design (FSD)

Фронтенд строго структурирован по методологии FSD (Next.js App Router).

### Иерархия слоев (сверху вниз):

1. `app/` — корневая инициализация приложения, роутинг Next.js, провайдеры, глобальные стили (`globals.css`).
2. `widgets/` — крупные самостоятельные блоки интерфейса:
   - `ChatConcierge` (левая колонка 480px: шапка, сообщения `ChatMessagesList`, автоскролл `useChatAutoScroll`, чипсы, голосовой ввод).
   - `HotelCanvas` (правая колонка: шапка выдачи, сетка карточек отелей).
3. `features/` — пользовательские интерактивные сценарии:
   - `voice-input` (голосовой ввод через Web Speech API и визуализатор аудио).
   - `quick-chips` (чипсы быстрых уточнений Disambiguation).
   - `book-room` (модалка бронирования номера с прозрачным чеком).
4. `entities/` — бизнес-сущности предметной области:
   - `hotel` (карточка `HotelCard`, бейдж `HotelScoreBadge`, типы `Hotel`).
   - `message` (элемент сообщения `ChatMessageItem`).
   - `thought` (элемент стрима мыслей `ThoughtStream`).
5. `shared/` — переиспользуемый инфраструктурный код:
   - `ui/` — дизайн-система (shadcn/ui примитивы).
   - `api/` — хук `useChatStream`, парсер потока `sseReader.ts` и редуктор `thoughtReducer.ts`.
   - `lib/` — утилиты (`cn`, форматирование цен `formatPrice`).
   - `config/` — дизайн-токены и конфигурация.

### Золотое правило: Public API (Barrel `index.ts`)

- Каждый слайс (`entities/hotel`, `features/voice-input` и т.д.) обязан иметь файл `index.ts`.
- Внешние импорты разрешены **только** через Public API:

  ```typescript
  // ПРАВИЛЬНО:
  import { HotelCard, type Hotel } from "@/entities/hotel";
  import { VoiceInputButton } from "@/features/voice-input";

  // ЗАПРЕЩЕНО (будет остановлено линтером):
  import { HotelCard } from "@/entities/hotel/ui/HotelCard";
  import { VoiceInputButton } from "@/features/voice-input/ui/VoiceInputButton";
  ```

- **Запрет кросс-импортов:** Модули внутри `features/` не могут импортировать другие модули из `features/`. Модули внутри `entities/` не могут импортировать другие `entities/`.
- Настроен линтер `eslint-plugin-boundaries`, гарантирующий соблюдение этих правил в CI и локально.

## 4. Дизайн-система: Dark Swiss Minimalist (Без хардкода HEX)

- **Строго запрещено** хардкодить цвета через HEX в JSX (`className="bg-[#0D0E11] text-[#2DD4BF]"` — ЗАПРЕЩЕНО!).
- Все токены вынесены в CSS-переменные темы в `src/app/globals.css`:
  - Фон страницы: `bg-background` (`#0D0E11`)
  - Карточки и панели: `bg-card` (`#16181D`)
  - Бордеры и разделители: `border-border` (`#242731`)
  - Акцентный цвет (Teal): `text-primary`, `bg-primary` (`#2DD4BF`)
  - Основной текст: `text-foreground` (`#F4F4F6`)
  - Второстепенный текст: `text-muted-foreground` (`#8E92A0`)
- Интерфейс оптимизирован под сплит-экран 1440x900 (десктоп хакатона).
- **Стандарты форматирования данных:**
  - Цены отображаются в рублях с неразрывным пробелом (например, `12 500 ₽`).
  - Все даты бронирования приводятся к единому формату локали (например, `15 мар 2026`).

## 5. Контракт Server-Sent Events (SSE) `/api/chat/stream`

Эндпоинт стримит события в формате SSE с прозрачной трансляцией этапов работы пайплайна:

- `event: thought`: ход мыслей агента в реальном времени (отражает реальный шаг пайплайна: разбор параметров, векторный поиск, фильтрация цен):
  ```json
  { "step": "search", "text": "Ищу отели в Красной Поляне с бассейном..." }
  ```
- `event: token`: потоковый чанк ответа консьержа:
  ```json
  { "content": "Я нашел отели, подходящие под ваш запрос." }
  ```
- `event: widget`: структурированный JSON для отображения виджетов на канвасе:
  ```json
  {
    "type": "hotel_grid",
    "hotels": [...],
    "disambiguation_chips": ["Дешевле 10 000 ₽", "С завтраком", "У подъемника"]
  }
  ```
- `event: done`: сигнал завершения генерации:
  ```json
  { "status": "ok" }
  ```

## 6. Запуск, проверка качества и скрипты проекта

В корневом `package.json` настроены команды:

| Команда                   | Что делает                                                    |
| ------------------------- | ------------------------------------------------------------- |
| `npm run dev`             | **Основная команда:** Запуск фронтенда и бэкенда в hot-reload |
| `npm run dev:static-back` | Запуск фронтенда в hot-reload, бэкенда — в статичном режиме   |
| `npm run dev:front`       | Запуск только фронтенда (Next.js на порту 3000)               |
| `npm run dev:back`        | Запуск только бэкенда (FastAPI на порту 8000 с `--reload`)    |
| `npm run lint`            | Проверка линтерами (ESLint + FSD Boundaries + типы бэкенда)   |
| `npm run test`            | Запуск всех тестов: 41 Vitest (фронт) + 39 Pytest (бэк)       |
| `npm run build`           | Проверка продакшн сборки фронтенда                            |

## 7. Памятка для будущих сессий и агентов

- **Тестовый барьер:** в проекте развернуто **80 автоматических тестов** (41 Vitest + 39 Pytest). Ни один коммит не может быть принят с падающими тестами (требуется 100% Pass Rate).
- **Соблюдение архитектуры SRP:**
  - При модификации поиска изменяются целевые сервисы: `vector_store.py` (ChromaDB), `hotel_filters.py` (фильтрация и скоринг), `location_registry.py` (города). Модуль `hotel_search_adapter.py` используется только как фасад.
  - При модификации работы с LLM изменяются: `llm_client.py` (вызовы API), `slot_extractor.py` (парсинг слотов), `thought_generator.py` (мысли) или `response_generator.py` (ответ консьержа). Модуль `llm_cascade.py` сохраняется как фасад.
- **Чистота Git и `.gitignore`:** перед коммитом всегда проверяется `git status`. Все временные бинарники, дампы отладки и динамические индексные файлы отсекаются через `.gitignore`.
- **Операционные правила агентов:** детальные регламенты зафиксированы в каталоге [`.agents/`](file:///c:/Users/vanya/OneDrive/Desktop/ostrovok2026/.agents/README.md) и его модулях в `.agents/rules/` (`frontend.md`, `backend.md`, `security-and-testing.md`, `git-workflow.md`).
