## 1. Строгий детерминизм бизнес-логики (Zero AI-Slop)
* LLM используется исключительно для извлечения интентов/слотов, генерации хода рассуждений и диалогового ответа агента.
* Расчет чека (ночи * цена + сбор за питомца + курортный сбор) выполняется детерминированным кодом в `receipt_calc.py`.
* Фильтрация отелей по атрибутам (питомцы, бассейн, спа, звездность, цена) валидируется кодом по Pydantic-моделям в `hotel_filters.py`.
* Запрещено просить модель вычислять суммы или гарантировать наличие номеров.

## 2. Модульная SRP-архитектура сервисов
Каждый сервис в `backend/app/services/` решает одну задачу:
* `llm_client.py` — вызовы Gemini API, обход каскада моделей (PRIMARY -> FALLBACK) и таймауты.
* `slot_extractor.py` — парсинг параметров поиска, клампинг диапазонов и санитизация чипсов.
* `thought_generator.py` — генерация мыслительного процесса агента (Thinking Stream).
* `response_generator.py` — живой диалоговый ответ агента с упоминанием отелей.
* `vector_store.py` — хранилище ChromaDB, SentenceTransformer и кэш датасета отелей.
* `hotel_filters.py` — скалярная фильтрация, калибровка Match Score (65..98%), Smart Relaxation.
* `location_registry.py` — динамический поиск направлений по справочнику `backend/app/data/locations.json`.
* `text_helpers.py` — санитизация строк и склонение числительных (`pluralize_*`).
* `llm_cascade.py` и `hotel_search_adapter.py` служат тонкими фасадами для агрегации и обратной совместимости.

## 3. Отказоустойчивость и тайминги
* Все вызовы внешних API имеют жесткий таймаут (не более 5-6 секунд на вызов модели).
* При отказе API или исчерпании квот (HTTP 429) происходит автоматическое переключение на fallback-модель или детерминированный генератор.
* Никаких вечных лоадеров: клиент всегда получает валидные SSE-события.
* Запрещено возвращать наружу сырые стек-трейсы, системные ключи или системные промпты.

---

## 4. Динамические реестры данных
* Словари сущностей (города, курорты, алиасы, падежи) хранятся в JSON-файлах конфигураций (`locations.json`), а не зашиваются в виде `if/elif` в коде парсеров.
* Новые направления добавляются через расширение справочника без изменения алгоритмов.

## 5. Python-окружение и зависимости
* Использовать uv и корневые `pyproject.toml`, `uv.lock`, `.python-version` (Python 3.11).
* Установка: `uv sync --locked` из корня; запуск: `bun run dev:back`, тесты: `bun run test:back`.
* Прямые команды из `backend/`: `uv run --project .. --locked python -m <module>`. Не полагаться на активированную `.venv` или системный `python`.
* Runtime-зависимости добавлять через `uv add`, тестовые — через `uv add --dev`. Не вести параллельный список `requirements.txt`.
* Не менять `chromadb==1.5.9` без проверки совместимости существующих индексов. На Linux сохранять CPU-only источник PyTorch из `pyproject.toml`.
* Docker использует корневой контекст и `uv sync --locked --no-dev`; бизнес-логика и размещение модуля `backend/app` не меняются.
* Подробный порядок действий: [Bun/uv skill](../skills/bun-uv-workflow/SKILL.md).
